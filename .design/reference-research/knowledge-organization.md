# P06 无代码知识组织参考研究

- 研究日期：2026-07-20（Asia/Shanghai）
- 范围：标签组合框、文档关系选择器、来源表单
- 约束：只复用现有 schema、RLS、RPC 与 P05 保存/恢复能力；不新增 migration，不接入 AI，不发起模型调用
- 目标用户：不理解 Markdown、UUID、数据库关系或内部 URL 的普通用户

## 1. 结论摘要

P06 应当是一个纯人工、可解释、可撤销的整理切片。用户通过名称和自然语言维护标签、知识关系与来源，界面内部再映射到现有 `tags`、`document_tags`、`document_links` 和 `document_sources`。任何界面都不得要求用户输入 UUID、内部路径或关系表字段。

推荐的最小闭环是：

1. 用可搜索组合框选择或显式创建标签。
2. 用文档标题搜索目标，并用完整句子确认关系方向。
3. 用“网页或文章 / 个人经验”两类来源表单记录依据。
4. 所有变更进入当前草稿，由 P05 的本地暂存、自动保存、版本冲突与恢复通道处理。

本切片不自动分类、不推荐标签、不推断关系、不抓取网页元数据，也不读写 `ai_suggestions`。未来 A23 可以在同一控件中呈现独立、待审阅的 AI 建议，但不能改变 P06 的人工输入语义。

## 2. 既有数据与安全边界

### 2.1 标签

现有 `20260718000300_document_organization.sql` 已提供：

- `tags`：`knowledge_base_id`、`owner_id`、`name`、`normalized_name`；显示名与规范名均为 1–80 个字符。
- 同一知识库内 `(knowledge_base_id, normalized_name)` 唯一。
- `document_tags`：以 `(document_id, tag_id)` 为主键，避免同一标签重复关联。
- `tags` 与 `document_tags` 均启用 owner RLS，读写条件为 `auth.uid() = owner_id`。

P06 只需把现有自由文本标签体验改为组合框，并通过当前认证用户的 RLS 路径读写上述表。不得为组合框新增表或放宽 RLS。

### 2.2 文档关系

现有 `document_links` 已提供：

- `from_document_id`、`to_document_id`、`owner_id`、`relation_type`、`note`。
- `relation_type` 仅允许 `prerequisite`、`related`、`continues`。
- `note` 最多 240 个字符。
- 主键为 `(from_document_id, to_document_id, relation_type)`，并有 `from_document_id <> to_document_id` 约束。
- 表已启用 owner RLS。

P06 必须沿用这三种关系，不增加新枚举。客户端检查只能改善反馈，数据库约束与 RLS 仍是最终边界。

### 2.3 来源

现有 `20260718000400_document_sources.sql` 已提供：

- `kind` 仅允许 `web` 或 `personal`。
- URL 最多 2,048 个字符；标题 240、作者 160、说明 1,000 个字符。
- `web` 必须是无空白的 HTTP/HTTPS URL。
- `personal` 必须有非空标题，且 URL 必须为 `NULL`。
- `(document_id, sort_order)` 唯一；列表顺序由 `sort_order` 表示。
- `document_sources` 已启用 owner RLS。
- `replace_document_sources(document_id, sources)` 先验证当前用户拥有且未软删除目标文档，再在一个数据库事务中替换来源列表；`PUBLIC` 与 `anon` 无执行权，仅 `authenticated` 可执行。
- RPC 最多接受 50 条来源；网页来源在写入时把 `accessed_at` 设为当天。

P06 继续使用该 RPC，不新增来源 migration。由于当前替换 RPC 会重写网页来源的 `accessed_at`，首版界面不展示或承诺“首次访问日期”。

### 2.4 保存与冲突

跨表保存目前仍可能出现正文成功、整理数据失败的部分成功状态。P05 已提供本地快照、outbox、版本冲突和恢复能力，P06 应把标签、关系与来源包含在同一草稿快照中，并遵循以下规则：

- 保存请求携带当前文档 revision/base version。
- 陈旧写入不得覆盖云端；进入现有冲突比较流程。
- 本地暂存成功不等于云端已保存，界面文案必须区分。
- 正文成功而整理数据失败时保留输入并显示：`正文已保存，整理信息暂未同步，请稍后重试。`
- 不向普通用户显示表名、SQL、migration 文件名或 RPC 错误原文。

## 3. 标签组合框最小规范

### 3.1 文案

| 场景             | 文案                                   |
| ---------------- | -------------------------------------- |
| 标签             | `标签`                                 |
| 帮助             | `从已有标签中选择，或创建一个新标签。` |
| 输入占位         | `搜索或输入标签名称`                   |
| 创建项           | `创建标签“{名称}”`                     |
| 无结果           | `没有匹配的标签`                       |
| 已存在           | `“{名称}”已在当前知识中`               |
| 过长             | `标签名称不能超过 80 个字符`           |
| 移除按钮辅助名称 | `移除标签“{名称}”`                     |

### 3.2 交互

- 已选标签以 chip 展示；选择已有结果后立即加入当前草稿。
- 只有激活明确的“创建标签”结果才创建新标签，不能把任意 Enter 自动解释成创建。
- 搜索及判重采用：首尾去空白、Unicode NFKC、大小写折叠、连续空白合并。显示名称保留用户确认的写法。
- 键盘支持上下方向键、Enter、Escape；输入为空时第一次 Backspace 选中最后一个 chip，第二次才移除。
- 服务端唯一约束命中时，重新选择已有标签，不显示泛化的“保存失败”。
- 从当前文档移除 chip 只删除 `document_tags` 关联，不删除 `tags` 实体。

### 3.3 防错

- 空白、纯标点或超过 80 字不能创建。
- 大小写、全半角和多余空格变体不能产生重复标签。
- 搜索仅限当前账户可见且属于当前知识库的标签。
- 加载或保存失败时保留输入；不得清空已选 chip。
- 不显示“AI 推荐”、置信度或自动分类入口。

## 4. 文档关系选择器最小规范

### 4.1 文案

| 场景     | 文案                                           |
| -------- | ---------------------------------------------- |
| 标题     | `知识关系`                                     |
| 帮助     | `选择另一条知识，并说明它与当前内容的关系。`   |
| 新增     | `＋ 添加关系`                                  |
| 搜索占位 | `按标题搜索自己的知识`                         |
| 无结果   | `没有找到可关联的知识`                         |
| 说明标签 | `关系说明（可选）`                             |
| 说明占位 | `用一句话说明为什么要建立这条关系`             |
| 自关联   | `不能把当前知识关联到自己`                     |
| 重复     | `这条关系已经存在`                             |
| 循环     | `这会形成循环的阅读顺序，请改选其他关系或文档` |
| 删除目标 | `原关联知识已删除`                             |

三种关系在确认前必须显示成完整句子：

- `prerequisite` / 前置知识：`阅读《当前文档》前，建议先读《目标文档》。`
- `related` / 相关知识：`《当前文档》与《目标文档》讨论相关主题。`
- `continues` / 继续阅读：`读完《当前文档》后，可以继续读《目标文档》。`

### 4.2 交互

- 先选择关系类型，再按标题搜索目标；搜索结果显示标题、所属知识库和可见性状态，不显示 UUID。
- 选择目标后先展示方向句，再允许确认。
- 关系说明可选，最多 240 字。
- `related` 若任一方向已存在，则定位已有关系，不创建镜像重复项。
- `prerequisite` 与 `continues` 在已加载的 owner 关系图中检查明显循环；发现时阻止提交并解释。
- 目标被软删除或失去访问权时，以“原关联知识已删除”降级显示并允许移除，不能让整个编辑器失败。

### 4.3 防错

- 禁止把当前文档关联到自己。
- 禁止粘贴 UUID、内部 URL 或网页地址代替文档选择。
- 不显示其他账户、软删除或无权限文档的标题及数量。
- 移除关系不删除目标文档。
- 客户端的重复/循环提示不替代数据库约束与 RLS。
- 不自动推断“前置”“相关”或“继续阅读”。

## 5. 来源表单最小规范

### 5.1 文案

| 场景         | 文案                                                       |
| ------------ | ---------------------------------------------------------- |
| 标题         | `引用来源`                                                 |
| 帮助         | `记录网页出处或你自己的实践经验；可以添加多条。`           |
| 新增         | `＋ 添加来源`                                              |
| 空状态       | `还没有来源。知识也可以先从个人理解开始，稍后再补充依据。` |
| 类型         | `网页或文章` / `个人经验`                                  |
| URL          | `网址`                                                     |
| URL 帮助     | `只接受以 http:// 或 https:// 开头的网址。`                |
| 标题         | `标题`                                                     |
| 标题占位     | `文章标题或经验名称`                                       |
| 作者         | `作者 / 提供者`                                            |
| 说明         | `这条来源说明了什么？`                                     |
| 说明占位     | `用一句话记录它与当前知识的关系（可选）`                   |
| 网页错误     | `请填写完整的 http:// 或 https:// 网址。`                  |
| 个人经验错误 | `请为个人经验写一个简短名称，方便以后辨认。`               |
| 数量错误     | `每条知识最多保留 50 条来源，请先合并或移除部分来源。`     |
| 移除状态     | `来源已从当前草稿移除；保存后同步到云端。`                 |

### 5.2 字段与交互

- 网页来源：URL 必填；标题、作者、说明可选，并遵守现有 240/160/1,000 字限制。
- 个人经验：标题必填；切换到该类型时隐藏并清空 URL；作者与说明可选。
- 仅接受 HTTP/HTTPS，拒绝 `javascript:`、`data:`、`file:` 等协议。
- 不自动访问 URL、不抓取标题或作者、不调用 AI 补全元数据。
- 完全相同的规范化 URL 再次添加时，定位已有来源并提示，不创建重复项。
- 不擅自删除查询参数，因为它们可能是来源定位的一部分。
- 对明显包含 token、密码或一次性登录参数的网址提示：`这个网址可能包含登录信息，请确认后再保存。`
- 移除来源只修改当前草稿；提供短时撤销，不弹频繁确认框。
- 首版按添加顺序保存，不新增拖拽排序能力。

### 5.3 防错

- 错误应定位到具体来源卡片和字段，而不是只在列表顶部显示。
- 切换来源类型时不得把网页 URL 留在 `personal` payload 中。
- 超过 50 条时禁止继续添加，并保留全部已有输入。
- 认证、网络或 RPC 失败时不清空来源列表。
- 普通用户不应看到“请执行某个 migration”之类技术提示。

## 6. 共同状态、可访问性与响应式

统一状态文案：

- `正在保存…`
- `已保存`
- `等待联网，修改已保存在本机`
- `文档已在其他页面更新，请先处理版本冲突`

最低验收：

- 所有输入有可见 label；状态通过 `role="status"` / `aria-live="polite"` 宣读。
- 组合框遵循 WAI-ARIA combobox/listbox 语义；焦点、展开状态和活动选项不能只依靠视觉判断。
- 全键盘可完成搜索、选择、新建、移除和撤销；关闭弹层后焦点返回触发控件。
- 错误不只依靠颜色；同时提供文字与字段关联。
- 320px 宽度下 chip、结果列表、关系方向句和来源卡片不造成页面级横向滚动。
- 删除目标、空列表、加载中、加载失败、离线与版本冲突都有独立状态。

## 7. 官方与既有范例结论

本研究只借鉴交互语义，不复制第三方代码、品牌资产或文案。

| 范例                                                                                  | 可借鉴结论                                                                    | 不照搬部分                                                                    |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| [WAI-ARIA APG Combobox Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)   | 输入框、弹出列表、活动选项、展开状态和键盘行为需要形成完整组合框语义          | APG 示例不是可直接复制的成品组件；样式与数据边界仍由 wouldkeep 实现           |
| [GOV.UK accessible-autocomplete](https://alphagov.github.io/accessible-autocomplete/) | 搜索选择应优先保证键盘和辅助技术可用，并为无结果与确认选择提供清晰反馈        | P06 不新增该依赖；只采用其可访问交互原则                                      |
| [Notion Relations & Rollups](https://www.notion.com/help/relations-and-rollups)       | 用户选择页面标题而不是内部 ID，关系目标应以可识别的页面信息呈现               | wouldkeep 不引入数据库属性编辑器，也不自动创建双向关系                        |
| [Zotero: Adding Items](https://www.zotero.org/support/adding_items_to_zotero)         | 来源应把 URL、标题、作者等元数据分字段呈现，并允许人工校正                    | P06 不抓取网页、不识别 DOI/ISBN、不新增书目 schema                            |
| wouldkeep 现有来源编辑器                                                              | `web/personal` 两种来源、明确错误、最多 50 条和失败保留输入已经形成可复用基础 | 不保留面向普通用户的 migration 提示；不把 datalist/自由文本当作最终关系选择器 |

## 8. 不建议模式

1. 用逗号分隔字符串编辑标签。
2. 按 Enter 静默创建拼写错误的新标签。
3. 让用户输入文档 UUID、Markdown 链接或内部 URL。
4. 用单个“相关文档”字段隐藏关系方向。
5. 自动建立双向或循环关系而不展示结果。
6. 自动打开用户提交的网址或抓取远程元数据。
7. 保存失败后清空标签、关系或来源。
8. 把本地暂存描述成“已同步到云端”。
9. 在 P06 中加入 AI 分类、建议置信度、模型设置或付费调用。
10. 为完成 UI 另加 migration、放宽 RLS 或开放匿名写 RPC。

## 9. 推荐实施与验收顺序

1. 先把标签自由文本改成 owner/knowledge-base 范围内的组合框与 chip。
2. 再把前置/相关自由文本或 datalist 改成文档标题搜索与方向确认。
3. 最后收紧现有来源表单的字段级错误、重复 URL、敏感 URL 警告和撤销反馈。
4. 用 owner、other-user、anonymous 三类会话证明搜索与写入隔离。
5. 用 P05 的刷新、离线、双标签冲突与版本恢复用例覆盖全部整理字段。
6. 在 320/375/800/1200px 和键盘路径验收后，再申请进入 PR 合并流程。

以上步骤均不需要新的数据库 migration 或 AI 能力。任何未来 schema/RLS/RPC 变更、生产部署或 AI 接入必须作为独立切片重新审查和授权。
